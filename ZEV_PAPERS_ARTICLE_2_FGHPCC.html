FG-HPCC: One Article

Mission · Vision · Security · Control plane · Use cases · LLNL/NNSA RFI

Introduction

The Future Generation High Performance Computing Center (FG-HPCC) is Lawrence Livermore National Security’s vision for the next step in NNSA computing.

It is not a single machine. It is a converged data center: HPC, AI training and inference, web services, analytics, and CI — composable, tightly integrated, and manageable through a common software stack.

This article walks through mission needs, gaps, the anticipated solution, security, the control plane, and the use cases that define what FG-HPCC must support.

1. Evolving mission needs

NNSA’s mission is evolving. The stockpile is aging; systems are refurbished, reused, or replaced.

Simulation: ASC simulations need more realism and accuracy to track aging. Better physics and solution methods mean greater computational demand. Weapon modernization will make up a large share of NNSA workload in the coming decade.

Collaboration: Design agency (DA) and production agency (PA) sites must work together. NNSA simulations increasingly use data and models from across the complex so that designs are optimized for real production.

Scale: HPC use cases will grow from single-site studies to a web of connected sites — iterating on design and production. Multi-physics codes must integrate more capabilities and reach more users. Simulation results must reflect the latest PA data and stay consistent with manufacturing.

2. Revolutionizing productivity

HPC procurements and GPUs have already cut simulation times from weeks to hours. GPUs will stay central for physical simulation and AI.

The bottleneck is often not runtime but human factors: complex workflows and cross-complex collaboration. NNSA tri-labs are therefore focused on developer and designer productivity.

FG-HPCC aims to accelerate the mission along three paths:

  • AI — Guide and accelerate large simulation workflows, understand complex phenomena, automate non-simulation tasks. AI synthesizes knowledge from data. NNSA workloads will couple more with AI; simulation ensembles will feed AI training.
  • Increased automation — AI, continuous deployment, ML models, workflow scheduling. Users set up and run large scientific workflows automatically and securely. Code teams build, test, and deploy automatically. ML-ops for versioning and managing models and software.
  • Persistent services — NNSA HPC applications become remotely accessible services. DA/PA share simulations, models, and data. Data in S3-like object storage; hosted web portals for codes, data, and AI models.

3. Future infrastructure vision and gaps

The vision: over 3 double-precision exaflops in peak capability, abundant utilities, and NNSA data centers that remain world-class. But those centers must evolve with the mission.

Gap 1 — Independent systems and difficult upgrades: Most HPC procurements deliver integrated systems; centers run independently. Incremental upgrades are hard and often force changes to unrelated resources.

Gap 2 — Limited security model: Current HPC centers rely on OS-level controls, trusted filesystems, and network zones. That model is too coarse for future NNSA needs. Strong isolation and multi-tenancy are missing.

Gap 3 — Inefficient resource management: Users specify resources explicitly via per-machine batch schedulers. Decomposed workflows with multiple interacting components are poorly supported. No common scheduling layer to coordinate disparate or disaggregated resources.

4. Anticipated solution — Center as a system

LLNS will transform the Livermore Computing (LC) system into a converged data center supporting HPC, AI training, AI inference, web services, analytics, and CI.

Users compose heterogeneous compute and storage into complex, orchestrated workflows. Resources are co-scheduled and orchestrated via common interfaces. Automated provisioning of compute, storage, and network tailored to jobs. Users provision and control the system through well-defined APIs.

Innovations: Multi-tenant hyperscale technologies; center-as-a-system deployment; cloud-like capabilities. Common open-source software stack; wider range of HPC/cloud vendors to avoid lock-in.

Procurement: Flexible strategy; multiple awards. Five major elements (from one or more vendors): (1) ModSim capability, (2) AI train/inference with ModSim, (3) compute for persistent data-intensive services, (4) center-wide storage, (5) high-speed data-center network. Transition over 4–5 years. Other NNSA labs (Sandia, LANL, KCNSC) can tailor and compose with strong isolation via a central data center network.

5. Open-source system software stack

LLNS builds on ASC. Key pieces: SLURM (batch scheduling), Flux (next-gen resource manager, e.g. El Capitan), TOSS (tri-lab OS, RHEL-derived, STIG for classified), ZFS on Linux (Lustre), Spack (package manager), OpenCHAMI and others.

The envisioned stack places traditional HPC alongside frameworks for services and AI, with primitives for strong isolation, control-plane APIs, and storage APIs. The RFI aims to assess designs and prioritize collaborations.

6. Security — Multi-tenancy, isolation, access control

Security is paramount. Traditional HPC is too coarse. Future elements must build in robust security from hardware to software.

Multi-tenancy: Multiple users at different security levels compose arbitrary subsets of resources. Strong logical separation where physical air gaps remain for classified vs unclassified.

Strong on- and off-node isolation: One user must not observe another’s data or actions. Fine-grained partitioning of CPUs, GPUs, network, and storage.

Flexible access control: Data owners control access. Role-based authentication. Filesystem authorization so a single node compromise does not breach the whole filesystem.

FG-HPCC resources must be usable for any workload without compromising security — batch, on-demand, persistent service, or untrusted CI. Secure node sharing; multiple tenants on same network or node. LLNS welcomes research into lowering overhead and cost for mission workloads.

7. Interoperability and data center control plane

Interoperability: Resources from different elements must work together with strong isolation. Example: ModSim + AI + I/O for an AI-augmented workflow. Resource manager (Flux or Kubernetes) establishes an isolated network via the Data Center Network Core. May require bridging different isolation mechanisms by 2030.

Control plane: Baseline storage, compute, and network allocation so users or facility staff build higher-level services or PaaS. Users compose FG-HPCC elements into private, isolated enclaves; elements can be added, upgraded, or removed without breaking workflows. RFI asks for open, on-premises, cloud-like control interfaces.

APIs: Low-level IaaS-style APIs; Sunfish, Redfish, S3, Terraform where available; open and documented otherwise. Management of nodes, VMs, network, storage, AI processors, volumes. In-band and out-of-band management.

Resource management: Flux for HPC allocation and scheduling; Kubernetes for facility and containerized user services. Flux+Kubernetes integration for converged HPC/cloud workflows. Guest OS: TOSS (RHEL-derived, STIG); virtualization and hypervisors with low overhead; network and storage isolation; complex-wide federation (e.g. DOE OneID, ESNHub).

8. Future use cases

AI-augmented simulation: ModSim + embedded AI surrogates and AI orchestration; blend double-precision ModSim with low-precision inference, ideally on the same node.

Digital twins: Twins of components at PA sites; AI monitors physical systems and integrates measurement streams; real-time and on-demand scheduling.

Inverse design: Generative AI explores design spaces; orchestrates large numbers of ModSim runs; informs designers or trains surrogates.

AI workloads: Campaigns, foundation models, data-surrogate models, HPC code assistants. Training from hundreds of hours to exaflop days. Data from TB to PB; read-mostly random-access or in-situ streams; provenance; data from NIF, AML, Vera Rubin, Scorpius.

Services and data-centric: More orchestration for runs, training, inference. Co-scheduled services, strong isolation. Persistent services connecting to production agencies; data warehouses and lakes; cross-site replication and versioning; flexible access control and need-to-know.

Developer workloads: Models and code versioned like code; CI for code and model changes; frequent model updates and human-in-the-loop; Jupyter, Colab, SageMaker; productive iteration inside FG-HPCC.

9. Collaborations and RFI

Respondents: high-level overview, capabilities, alignment. LLNS interested in HPC market impact and broad adoption. Collaborations: open-source, hardware/software testing, hardening, standardization. No mandated architecture.

Roadmap: Security/isolation; processors for ModSim and AI; virtualization; I/O and storage; secure DC networks; long-range connectivity; open-source stack; PaaS; other.

Gaps: Technologies unusable in HPC (overheads, latencies); software stack gaps for cloud-like on-prem; standardization with open-source. Software collaboration: isolation, encryption, network virtualization, MPI/libs/GPU in virtualized/containerized envs, open APIs and control planes.

Other: Standards; testing at LC; AI accelerator integration. Hardware: testbeds, test/prove/harden under NDA.

Review: Tri-labs + DOE Sci + federal. Two purposes: awareness of tech developments; prioritize industry/NNSA collaborations. Timeline: responses due 2025 Aug 8; review late Aug/Sep; feedback Fall/Winter 2025.

Closing

FG-HPCC is a vision for a converged NNSA data center: mission-driven productivity through AI, automation, and persistent services; security and isolation for multi-tenancy; common open-source stack and control plane; use cases that blend ModSim, AI, digital twins, inverse design, and data-centric workflows.

The RFI gathers information, assesses the stack and its gaps, and prioritizes collaborations. One article cannot replace the full document, but it summarizes the main threads so that nerds, hospitals, and government can see what FG-HPCC is and why it matters.
